# 知鉴 Search

> 把知乎上各说各话的二十篇经验，压成一张能下决定的卡片。

知乎黑客松 S3 · **AI × 知识与探索** 赛道参赛作品

**在线体验**：http://47.238.165.6:8000/app/　（真实检索，可直接输入任意问题）

---

## 它解决什么问题

搜「全屋定制怎么避免被坑」，知乎会给你 20 篇回答——其中一大半是商家在讲自家套餐。
用户要花 30 分钟才能判断该信谁，最后往往还是不敢下单。

知鉴把这 30 分钟压缩到 2 分钟：

- 把明显在卖东西的挑出来，**写明为什么**，但不删除（判断权归用户）
- 把「大家都这么说」「说法不一」「有人踩过的坑」分成三块摆出来
- 每条标出处、时间、赞同数，可回到原文
- 最后给一句能指导决策的结论——抽不出来时就说抽不出来

## 它不是什么

这三条比上面那段更重要，因为它们决定了我们没做什么：

- **不是「更准的搜索」。** 检索是商品，判断才稀缺。比「搜得全」我们赢不了，也不打算比
- **不是 RAG 套壳。** 核心在过滤判据与呈现方式，不在于调了一次模型
- **不替用户下结论。** 低可信内容会被收起、标注原因、可展开、可被用户推翻——
  这是产品主张，也是它和「AI 直接给答案」的根本区别

## 三条实测结论（都来自真实数据，可复现）

**① 软文密度远高于预期**
「两千价位扫地机器人 石头 追觅 怎么选」的 10 条结果里，8 条是导购；
「全屋定制有哪些坑」的 10 条里，5 条是商家自述（账号名就叫「宁波原木定制工厂」）。

**② 高赞不等于可信**
赞 1990 的那篇《2026 年扫地机器人推荐》，开头是「京东双十一…京享红包最高 26888 元」，
是教科书级导购。而真正给出具体生活条件的那条（套内 100㎡、没留上下水、有狗毛和长发），
只有 1 个赞。

**③ 改写查询本身就是最有效的过滤**
原始 query 的软文比例 40%；拆成「缺点 问题 后悔」「耗材 一年 花多少钱」
「基站 尺寸 上下水 预留」之后，降到 2.5%。
因为商家只投「哪个好」这类购买决策词，不投具体问题词。

## 快速开始

```bash
# 1. 起后端
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --port 8000

# 2. 打开界面
# 浏览器打开 prototype/index.html
```

**不需要任何 API Key 也能跑**：后端连不上时前端自动退回本地演示数据，
并在界面上标明当前模式。这是刻意设计的——评委在现场网络不稳时仍能完整体验。

需要用真实检索时，配置两项：

```bash
# 知乎开放平台凭据（用于取真实内容）
export ZHIHU_CLI_PATH=/path/to/zhihu-cli

# 可选的模型 Key（用于生成结论，没有则退回关键词抽取）
cp backend/.env.example backend/.env  # 填入 DEEPSEEK_API_KEY
```

## 技术实现

**五阶段流程**

```
改写查询 → 多路召回 → 去重 → 时效过滤 → 可信度质检 → 归并成三段
```

每个阶段的处理量与剔除原因都写进 `trace`，前端可以展示「这些结果是怎么挑出来的」。

**几个关键取舍**

| 约束（实测） | 应对 | 代价 |
|---|---|---|
| 单次检索最多 10 条，不能翻页 | 拆 3–5 个子查询分别召回后合并 | 一次查询消耗多次额度，子查询质量决定上限 |
| 返回的是命中片段，不是全文 | 只做观点级提炼 | 卡片细节颗粒度变粗，无法引用完整论证 |
| 高赞内容大概率是导购 | 可信度不以点赞为主要权重 | 与用户「高赞=好」的直觉冲突，需要界面解释 |
| 纯规则抓不住「结论」 | 接模型做摘要，失败退回关键词抽取 | 多 2–3 秒延迟，且依赖外部服务 |

**过滤设计**

判据全部放在 `backend/rules.json` 里，改规则不需要改代码。
输出给用户的是人话理由（「文末有购买链接」），不是分数（0.62）。
