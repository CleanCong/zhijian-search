# 技术架构设计

> 项目：Vibe 科普大赏
> 版本：v1.0
> 日期：2026-11-26
> 约束：9–10 天开发周期，黑客松 MVP

---

## 一、定位

**核心判断：这不是一个 AI 视频生成器，而是一个知识引擎。**

```
知乎内容（主要入口）
    ↓  以 Claim / Evidence 为组织基础
知识引擎（理解与重组）
    ↓  以图文动态演示为表达方式
用户（获取 → 理解 → 探索）
```

产品的价值不在"生成画面"，而在**把社区里零散、相互矛盾、夹带营销的经验，整理成有依据、有争议、有边界的知识结构**。

四个要素按重要性排序：

| 要素 | 作用 | 缺了会怎样 |
|---|---|---|
| Claim + Evidence | 知识组织基础 | 退化成"搜索结果摘要" |
| 检索与过滤 | 材料质量 | 垃圾进，垃圾出 |
| 图文动态演示 | 表达方式 | 用户看不懂，但知识结构还在 |
| 追问与关联 | 探索闭环 | 一次性消费，不是"探索" |

### 三条不可动摇的原则

开发过程中如遇取舍，按这三条排序：

| # | 原则 | 意味着 |
|---|---|---|
| 1 | **知识包优先于视频** | 知识包正确，展示形式才有意义。宁可播放器简陋，不可知识错误 |
| 2 | **证据优先于结论** | 没有来源支撑的内容，不能包装成确定事实。宁可说"材料不足" |
| 3 | **复用优先于重复生成** | 深度切换、追问、关联探索，尽量复用已有知识包，不重新检索 |

第 3 条既是体验要求（切换要快），也是额度约束（知乎 5000 次额度是硬上限）。

## 二、总体架构

系统拆成三层，**层间只通过明确的数据契约通信**：

```
┌─────────────────────────────────────────────────┐
│  产品呈现层  React + Vite                        │
│  问题输入 · 深度切换 · 图文播放器 · 来源展示       │
│  追问 · 关联知识                                 │
└──────────────────┬──────────────────────────────┘
                   │ REST / JSON（异步任务 + 轮询/SSE）
┌──────────────────▼──────────────────────────────┐
│  应用编排层  FastAPI                             │
│  ┌────────────┬────────────┬──────────────┐     │
│  │ 任务管理   │ 检索规划   │ 知识处理     │     │
│  │ 状态/队列  │ 意图/预算  │ Claim/Evidence│    │
│  └────────────┴────────────┴──────────────┘     │
└──────────────────┬──────────────────────────────┘
                   │
      ┌────────────┴────────────┐
      ▼                         ▼
┌──────────────────┐  ┌──────────────────────────┐
│ 检索适配层        │  │ AI 能力层                │
│ 知乎搜索          │  │ DeepSeek（结构化输出）    │
│ 全网搜索          │  │ TTS（旁白配音）           │
│ 知乎直答          │  │ 可选：图片生成            │
│ 回答摘要          │  └──────────────────────────┘
│ 热榜 / 问题发现   │
└──────────────────┘
                   │
┌──────────────────▼──────────────────────────────┐
│  持久化与缓存层  SQLite + JSON                   │
│  任务记录 · 知识包 · 来源 · Trace · 检索缓存     │
└─────────────────────────────────────────────────┘
```

## 三、技术选型

| 层级 | 选型 | 理由 |
|---|---|---|
| 前端 | React + Vite | 播放器需要组件化与时间轴状态管理 |
| 后端 | Python + FastAPI | 复用现有后端与 LLM 调用封装 |
| LLM | DeepSeek `deepseek-chat` | 复用现有调用，已验证结构化 JSON 输出能力 |
| 检索 | 知乎开放平台 CLI / API | 保留已有能力 |
| 外部补充 | 知乎全网搜索 | 补充官网、新闻、论文类事实 |
| TTS | 现有可用 TTS API | 旁白配音 |
| 数据库 | SQLite（WAL 模式） | 单机部署，无需运维 |
| 缓存 | JSON 文件 + SQLite | 复用现有缓存经验 |
| 演示 | React 时间轴播放器 | 不依赖视频渲染 |
| 部署 | 阿里云 ECS + systemd | 延续现有部署方式 |

### 三个刻意的技术取舍

**① 不上向量数据库**

现有项目没有 Embedding、向量库和数据库基础。9–10 天内引入完整向量检索体系会显著增加工程风险。

首期用「LLM 规划检索 + 规则去重 + 原子 Claim 抽取 + 语义归并」完成知识组织。

**触发引入 Embedding 的条件**（不是"以后再说"）：
- Claim 去重准确率低于 70%
- 同一 Claim 在不同表述下无法归并
- 材料超过 100 条后检索质量明显下降

**② 不用 Remotion / FFmpeg 作为 MVP 必要依赖**

前端播放器按结构化脚本切换文字、图片、图表、字幕，TTS 音频独立播放。

体验上是"视频"，工程上不需要等待视频文件渲染。**降低了一半的失败面**。

**③ 检索与生成分离**

检索结果与知识包持久化，脚本按深度单独生成。

同一问题切换深度、追问、重新播放，**都不重新调用检索接口**。这既是体验要求，也是额度约束。

## 四、核心数据流

```
1. 用户提交问题
   query + depth（入门/进阶/专业）+ 可选上下文
        ↓
2. LLM 动态检索规划
   判断问题类型 → 拆子问题 → 选来源 → 定预算
        ↓
3. 多源检索
   知乎搜索（主）· 全网搜索（补）· 按需直答/摘要/问题发现
        ↓
4. 材料标准化
   统一字段 · 去重 · 记录来源 · 保留原文片段
        ↓
5. 知识提取
   原子 Claim · Evidence 关联 · 冲突识别 · 覆盖检查
        ↓
6. 构建 Knowledge Package
   共识 · 不同观点 · 未解问题 · 类比 · 术语表 · 来源
        ↓
7. 生成讲解内容
   按深度生成时间轴脚本（Scene 数组）
        ↓
8. 播放与探索
   图文动态 · 配音 · 来源跳转 · 追问 · 关联问题
```

## 五、关键原则：知乎直答不能代替证据

六种知乎能力职责不同，混用会产生**虚假的交叉验证**：

| 能力 | 定位 | 能否作为独立证据 |
|---|---|---|
| 知乎搜索 | 社区观点、经验、回答片段 | ✅ 可以 |
| 问题回答摘要 | 原回答摘要 + 链接 | ✅ 可以，但须标记为摘要 |
| 全网搜索 | 官网、新闻、论文 | ✅ 可以，须保留来源 |
| **知乎直答** | 快速综合答案、知识提取辅助 | ❌ **不可单独作为证据** |
| 知乎热榜 | 发现热点选题 | ❌ 不作为事实证据 |
| 问题发现 | 发现真实存在的问题 | ❌ 不作为事实证据 |

### 必须避免的错误

```
知乎直答生成的综合答案
    + 它引用的那几篇知乎回答
    ≠ 两个独立证据
```

这两者**同源**。把它们计作交叉验证，等于自己给自己作证。

**规则**：Evidence 必须能追溯到真实 URL；`source_type = zhihu_direct_answer` 的记录，在 UI 上标注为「AI 综合」，且不进入「多方印证」的计数。

## 六、与现有「知鉴 Search」项目的关系

本方案是在现有代码上演进，不是重写。

| 层 | 现有资产 | 处理方式 |
|---|---|---|
| 检索封装 | `backend/zhihu.py`（CLI 调用、编码、超时、错误） | ✅ **直接继承** |
| 过滤判据 | `backend/rules.json`（11 条）+ `evaluate.py`（评测） | ✅ **直接继承**，后续扩展 |
| 归并逻辑 | `backend/merge.py`（共识/分歧/坑） | 🔶 **演进**：整篇归组 → 原子 Claim 抽取 |
| LLM 调用 | `backend/llm.py`（结构化 JSON + 失败降级） | ✅ **继承**，扩展 prompt |
| 缓存 | `backend/cache.py`（24h 文件缓存） | 🔶 **扩展**：增加中间结果级缓存 |
| 部署 | `deploy/` + `scripts/` + systemd | ✅ **继承** |
| 前端 | `prototype/`（原生 JS，约 900 行） | ❌ **重写为 React** |
| Trace | 六阶段人话描述 | 🔶 **升级**为结构化事件（含耗时、数量） |

### 演进而非重写的核心证据

现有 `merge.py` 做的「判断立场 → 分共识/分歧/坑」，本质上**已经是粗粒度的观点组织**。

新方案的 Claim 化，是把粒度从「一篇回答」降到「一句断言」——**同一套思路，更细的尺子**。

因此 `merge.py` 里的词表（坑信号词、场景词、立场词）可以**直接迁移**到 `claim_extractor` 和 `conflict_detector`，不用从零调。

## 七、主要工程风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **生成延迟 15–25 秒** | 同步 HTTP 会超时、用户流失 | 必须异步任务 + 进度推送（见 API 设计） |
| Claim 抽取质量不稳 | 整个产品的核心质量 | 词表继承现有资产；反幻觉检查（见测试方案） |
| 前端重写吃掉工期 | React 版播放器从零开发 | 播放器先做「能播」，视觉后补 |
| 多源检索额度冲突 | 演示时额度耗尽 | 检索预算模块 + 缓存预热 |
| LLM 返回非法 JSON | 链路中断 | 重试 + 严格 schema 校验 + 降级 |

## 八、讲解深度与知识包解耦

这是整个架构中最值得坚持的一条设计。

```
                 ┌── 入门：生活类比、场景化解释
Knowledge Package ┼── 进阶：机制原理、关键逻辑
（同一份）        └── 专业：技术细节、限定条件、前沿争议
```

**同一个 Knowledge Package，三种深度只重新生成脚本，不重新检索、不重新构建知识包。**

### 为什么必须这样

如果三种深度各自独立检索、独立总结，会出现两个严重问题：

1. **依据不同**：入门版说 A，专业版说 B，用户切换后看到互相矛盾的结论
2. **成本翻三倍**：三次检索、三次 Claim 抽取，额度和延迟都不可接受

### 深度的实质差异在哪

不是换一段 prompt 的语气，而是**选材与展开方式的差异**：

| 深度 | 保留什么 | 舍弃什么 | 展开方式 |
|---|---|---|---|
| 入门 | 核心结论、生活类比、最常见误区 | 技术参数、限定条件、学术争议 | 「就像……」 |
| 进阶 | 加上机制、因果链、适用边界 | 公式推导、文献引用 | 「因为……所以……」 |
| 专业 | 全部保留，含争议、未解问题、前沿 | 无 | 「在 X 条件下成立，Y 情况下例外」 |

**底层依据必须一致**：三种版本引用的 Claim 是同一组，只是选取子集和解释深度不同。

## 九、内容使用边界（合规）

这既是法律问题，也是项目可信度的一部分。

### MVP 遵循的五条规则

| 规则 | 具体做法 |
|---|---|
| 只使用授权接口 | 不爬取、不绕过接口限额、不使用非开放平台渠道 |
| 保存最小必要信息 | 引用片段 + 来源 URL + 作者 + 发布时间，不存全文镜像 |
| 展示时标注来源 | 每条 Claim 可追溯到「知乎 · 作者名 · 原文链接」 |
| 不重新包装成自有内容 | 输出是「加工后的判断 + 引用」，不是「改写过的文章」 |
| 标注 AI 生成属性 | 知乎直答等综合答案，UI 明确标「AI 综合」，与真实回答区分 |

### 对来源不足的处理

来源不可访问、或只有单一来源时，**必须显式提示**，不能沉默地当已证实内容展示。

这与「证据不足就说不足」是同一个原则，只是从知识层延伸到了展示层。

## 十、不做的事（明确边界）

| 不做 | 原因 |
|---|---|
| 向量数据库 / Embedding | 9–10 天不够，且有替代方案 |
| 视频文件渲染（Remotion/FFmpeg） | 图文动态已足够表达，渲染是额外失败点 |
| 用户账号 / 收藏 / 学习历史 | 不进入 MVP |
| 多实例部署 | 单机足够，SQLite 不支持多实例 |
| 知识图谱数据库 | 首期 7 张表够用 |
| 自动发布到社交平台 | 与赛题无关 |
