# 分阶段开发路线图

> 项目：Vibe 科普大赏
> 版本：v1.0
> 日期：2026-11-26
> 周期：9–10 天

---

## 一、总体策略

**不按模块平均分配时间，而是先跑通一条端到端链路，再补深度。**

```
第 1–2 天   地基：数据契约 + 检索打通
第 3–5 天   核心：Claim/Evidence + 知识包 + 播放器
第 6–7 天   体验与稳定：TTS + 交互 + 缓存
第 8–9 天   质量：测试 + Demo 打磨
第 10 天    缓冲（可选）
```

**关键判断：第 3 天和第 5 天是风险最高的两天。** 前者决定知识质量，后者决定"能不能看"。

---

## 二、十天计划

### 第 1 天 · 架构骨架与契约冻结

| 任务 | 交付物 |
|---|---|
| 核对现有代码边界（不按假定目录重写） | 继承清单：哪些复用、哪些改造、哪些新建 |
| 实测各接口返回结构与额度 | 接口实测记录（字段、耗时、失败形态） |
| 定义 Pydantic 模型 | `models/` 五个文件 |
| 确定 SQLite 表结构 | `001_init.sql` + 建表验证 |
| 冻结 API 契约 | `04-api.md` 定稿，前后端各自开工 |

**验收**：三个人对数据模型的字段名和含义没有分歧。

> 这一天必须做「核对」而不是「假定」。方案里的目录结构是目标，不是现状。先确认 `zhihu.py`、`merge.py`、`rules.json` 实际能提供什么，再决定新模块怎么接。

---

### 第 2 天 · 动态检索规划与多源召回

| 任务 | 交付物 |
|---|---|
| 用 LLM 替代固定模板做主规划 | `query_planner.py` + `prompts/query_planner.md` |
| 接入知乎搜索与全网搜索 | `zhihu_adapter` / `global_adapter` |
| 按预算调用直答与摘要 | `answer_adapter` + `retrieval_budget` |
| 统一标准化、去重、L1/L2 缓存 | `result_normalizer` / `deduplicator` / `content_cache` |

**验收**：输入任意问题，能返回 30–50 条带来源的 Evidence，去重后无重复 URL。

**降级方案**：如果 LLM 规划不稳定，**保留现有固定模板作为兜底**——`pipeline.py` 里的场景模板还能用，不要让第 2 天卡死在规划器上。

---

### 第 3 天 · Claim 提取与 Evidence 关联 ⚠️ 最紧

| 任务 | 交付物 |
|---|---|
| 回答拆成原子 Claim | `claim_extractor.py` + prompt |
| Claim ↔ Evidence 多对多 | `claim_evidence` 表写入 |
| 支持/反驳/补充关系识别 | `evidence_matcher.py` |
| 计算 `evidence_status` | `evidence_validator.py`（按 `independence_key` 去重后计数） |
| 覆盖检查 | `coverage_checker.py` |

**验收**：一篇含三个观点的回答，能拆出 ≥2 条 Claim；每条 Claim 至少关联 1 条 Evidence。

**这是全项目质量的核心**。质量调优可以放到第 8 天，但**链路必须在第 3 天打通**。

**降级方案**：如果一天做不完抽取 + 关联 + 校验三件事，**优先保「抽取 + 关联」**，`evidence_validator` 先用简化规则（来源数 ≥2 即 supported）。

---

### 第 4 天 · Knowledge Package

| 任务 | 交付物 |
|---|---|
| 组装知识包 | `knowledge_builder.py` |
| 共识与争议分析 | `consensus_analyzer.py` |
| 类比、术语表 | `analogy_generator` / `glossary_generator` |
| 关联问题（**此时生成并落库**） | `related_question_generator.py` |

**验收**：`GET /packages/{id}` 能返回包含 Claims / Evidence / 共识 / 争议 / 未解问题 / 类比 / 术语 / 关联问题的完整包。

---

### 第 5 天 · 脚本生成与图文播放器 ⚠️ 也紧

| 任务 | 交付物 |
|---|---|
| Scene JSON 契约 | `models/script.py` |
| 三档深度 prompt | `prompts/script_generator.md` |
| 前端时间轴播放器 | React 组件 |
| 字幕、插图、术语高亮 | 前端渲染 |
| 基础播放控制 | 播放/暂停/进度 |

**验收**：输入问题 → 能看到一段 60 秒左右、字幕与画面同步的图文演示。

**降级方案**（按顺序砍）：

```
1. 先砍 chart / formula 两种 visual.type，只留 illustration / text / comparison
2. 再砍「术语高亮点击查词典」，只保留高亮不联动
3. 播放控制只做「播放/暂停/重播」，不做拖动进度条
```

**这一天只求「能看」，视觉效果留到第 9 天。**

---

### 第 6 天 · 配音、来源展示与交互

| 任务 | 交付物 |
|---|---|
| TTS **按 Scene 分段**合成 | `tts_adapter` + `audio_manager` |
| 音频时长反推时间轴 | 更新 `start_ms` / `end_ms` |
| 来源展示 | 每条 Claim 可展开看原文链接 |
| 关联问题 | 点击可启动新任务 |
| 追问 | `POST /packages/{id}/questions` |

**验收**：有声音、字幕对得上、能点来源、能追问、能点关联问题开始新一轮。

**注意**：音画同步是本日最容易超时的部分。如果 TTS 分段后时间轴仍需手动调整，**接受 0.5 秒内的误差**，不要追求精确对齐。

---

### 第 7 天 · 缓存、任务管理与稳定性

| 任务 | 交付物 |
|---|---|
| 任务状态机与进度 | `generation_tasks` 表 + 轮询接口 |
| L3–L5 缓存 | `cache_entries` 表 + 版本化 key |
| 超时、重试、部分失败 | `partial_failed` 状态与前端提示 |
| 并发限制 | `rate_limiter` 串行控制 |

**验收**：任务崩溃不影响服务；切换深度不重新检索；相同问题第二次生成走缓存（<2 秒）。

---

### 第 8 天 · 测试与质量修复

| 任务 | 交付物 |
|---|---|
| 跑测试题库（见测试方案） | 问题清单与修复记录 |
| 反幻觉抽查 | 20 条 Claim 人工核对 Evidence |
| Claim 与 Evidence 对应关系检查 | 正确率记录 |

**验收**：抽查的 20 条 Claim 中，找不到来源依据的 ≤2 条（90% 可溯源）。

---

### 第 9 天 · Demo 优化

| 任务 | 交付物 |
|---|---|
| 三个演示问题定稿 | 见「Demo 设计」 |
| 预热缓存 | 三个问题提前跑一遍，现场秒开 |
| 播放器视觉优化 | 排版、配色、转场 |
| Trace 展示优化 | 技术抽屉的结构化数字 |
| 现场异常演练 | 断网、额度耗尽、LLM 超时的降级表现 |

**验收**：三个问题在**断网情况下**也能完整播放（走缓存）。

---

### 第 10 天 · 缓冲与冻结（可选）

- 处理剩余 Bug
- 端到端全流程回归
- 部署与启动流程复核
- **冻结功能，禁止引入新改动**

## 三、关键路径与并行分工

```
第 1 天  ──── 契约冻结（三人共同，必须同步完成）
              │
     ┌────────┼────────┐
     ▼        ▼        ▼
   A：后端   B：前端   C：质量
```

| 角色 | 负责 | 前置依赖 |
|---|---|---|
| **A（后端/知识引擎）** | 检索层、Claim/Evidence、知识包、脚本生成 | 第 1 天契约 |
| **B（前端）** | React 重写、播放器、来源展示、追问 UI | 第 1 天契约 + 第 5 天脚本契约 |
| **C（质量/数据）** | 测试题库、标注、反幻觉抽查、Demo 脚本 | 第 3 天后才能开始 |

**并行前提**：第 1 天必须把 `models/` 和 API 契约定死。否则第 5 天会在前后端对接上返工。

**B 的独立工作**：在 A 完成第 3 天之前，B 可以用**假数据**（按 Scene JSON 契约构造的样例）先做播放器，不阻塞。

## 四、砍单优先级

时间不够时，按这个顺序砍（从下往上）：

| 优先级 | 内容 | 能不能砍 |
|---|---|---|
| **P0** | 多源检索、Claim/Evidence、知识包、图文播放、来源展示 | ❌ 不能砍 |
| **P1** | 三档深度 | 🔶 可砍成两档（入门 + 专业） |
| **P1** | TTS 配音 | 🔶 可砍，纯字幕版反而更自洽（"图文动态，不是视频"） |
| **P1** | 关联问题 | ❌ 不建议砍，是探索闭环的关键 |
| **P1** | 追问 | ❌ 不建议砍，是差异化亮点 |
| **P2** | 图表 / 公式两种 visual.type | ✅ 可砍 |
| **P2** | 用户账户、收藏、学习历史 | ✅ 不在 MVP |
| **P2** | 完整知识图谱 | ✅ 不在 MVP |

**砍的顺序**：图表公式 → 三档改两档 → TTS → 停。

追问和来源展示是最后才考虑的，因为它们决定「这是不是一个可信的知识产品」。

## 五、Demo 设计

准备三个不同性质的问题，覆盖三种能力：

| # | 问题 | 展示什么 | 重要性 |
|---|---|---|---|
| 1 | 量子纠缠是什么？ | 类比、术语、科学原理 | 基础能力 |
| 2 | XX 技术安全吗？ | 多来源验证、争议、未解问题 | **最重要** |
| 3 | 某个产品应该怎么选？ | 知乎真实经验、不同观点、具体案例 | 落地感 |

### 为什么第 2 个最重要

它能让评委看到：**系统不是把搜索结果简单总结，而是能识别不同立场、呈现证据关系，并且不强行给出一个看似确定的最终答案。**

这正是这个产品和"AI 摘要工具"的分水岭。

### Demo 流程（约 4 分钟）

```
0:00  输入问题，展示检索进度（技术抽屉打开）
0:30  知识包概览：12 条 Claim，8 条有来源支持，3 条存在争议
1:00  播放入门版讲解（30 秒片段）
1:40  点开一条 Claim 的来源，展示原文链接
2:00  切换到专业版（不重新检索，秒切）
2:30  展示「存在争议」的部分——不做结论，呈现双方
3:00  点关联问题，开始新一轮
3:30  收尾：一句话定位
```

## 六、冻结策略

```
第 9 天 22:00  功能冻结，此后只修 Bug
第 10 天        只做回归与部署复核
```

**冻结之后不再做的事**：

- 改数据模型
- 换 prompt 主策略
- 加新接口
- 调整缓存 key 规则

这些改动的影响面都是全链路的，在最后两天做等于赌博。
