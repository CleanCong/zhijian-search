## 二、任务拆解与依赖

### 阶段划分

```
P0 计划书第一遍 ─────────────────────────┐（不依赖代码，可立即并行）
                                        │
P1 接口契约定义 ──┬── P2a 后端最小闭环 ──┤
                  └── P2b 前端字段映射 ──┴── P3 联调 ── P4 功能补全
                                                          │
                                        P5 部署公网 ◄─────┘
                                             │
                              ┌──────────────┴──────────────┐
                          P6 计划书第二遍              P7 演示视频
                                             │
                                        P8 提交前验收
```

### 任务明细

| 阶段 | 任务 | 产出 | 依赖 | 说明 |
|---|---|---|---|---|
| **P0** | 计划书第一遍 | 计划书初稿（定位/痛点/体验/生态/开放能力） | 无 | 不依赖代码，用实测数据支撑，占初审 40% 的主体 |
| **P1** | 接口契约 | 一份 `api-contract.md` | P0 的产品定义 | **前后端并行的前提**，必须先冻结 |
| **P2a** | 后端最小闭环 | `POST /api/search` 可用 | P1 | 五阶段：改写→多路召回→时效→质检→归并 |
| **P2b** | 前端字段映射 | 真实数据能渲染 | P1 | 与 P2a 并行，用 P2a 的 mock 响应先跑 |
| **P3** | 联调 | 真数据端到端跑通 | P2a + P2b | 双模切换（真数据 / 降级数据） |
| **P4** | 功能补全 | 勾选重组+导出、降权展开+推翻、状态齐全 | P3 | 现原型中两个按钮是占位，必须做成真的 |
| **P5** | 部署公网 | 可访问链接 | P3 | **风险最高的环节，见第四节 R1** |
| **P6** | 计划书第二遍 | 补技术实现 + 约束→应对→代价 | P3、P5 | 这部分必须等代码跑过才写得实 |
| **P7** | 演示视频 | 90 秒视频 | P5 | 录公网版，不录本地版 |
| **P8** | 提交前验收 | 逐项打勾 | 全部 | 按官方 9 条检查清单逐条过 |

### 关键依赖（不能颠倒的三处）

1. **P1 契约必须先于 P2a/P2b**——否则前后端字段必然打架，返工成本最高
2. **P5 部署必须先于 P7 视频**——视频必须录公网版，否则评委看到的环境和视频里不一致
3. **P6 计划书第二遍必须在 P3 之后**——技术章节的价值全在「我们碰到的真实约束」，提前写只能是设想

## 四、关键风险

按「发生后是否会直接导致交不上」排序：

### R1 · 知乎 CLI 无法在公网服务器运行〔致命〕

**问题**：CLI 的凭据存在本机 keychain 里。若后端部署到云服务器，服务器上没有这份凭据，`search` 会失败；而演示链接必须是公网可访问的。

**两条应对路线**：

- **A. 内网穿透 + 本地后端**：后端跑在本机，用隧道工具映射到公网。快，但依赖本机常开与网络稳定，演示期一旦断线链接就废
- **B. 云端后端 + HTTP API 直连**：后端部署到云服务器，用 `ZHIHU_ACCESS_SECRET` 环境变量传入凭据，直接调知乎开放平台 HTTP 接口（参考 `references/http-api.md`）。稳，但需要重新生成一份 Secret 给服务器用

**建议 B**，因为「评委点开链接」这件事不能依赖任何人的笔记本。但需要先验证：CLI 走的是哪套接口、能否用环境变量在无头环境工作。

**必须在 P5 之前做完这个验证**，不能等到部署当天。

### R2 · 密钥泄露

官方检查第 6 条：App Key / Access Secret / Token 不得出现在源码、前端响应、日志、截图、视频。

**应对**：密钥只从服务器环境变量读取；仓库里放 `.env.example` 不放真实值；提交前全仓库搜一次 `secret`/`token`/`appkey` 关键词。

### R3 · 演示不可复现

同一次检索两次调用结果可能不同，现场演示时结果变了就尴尬。

**应对**：后端加缓存层，同一个 query 24 小时内返回同一份结果；演示前预跑一遍热缓存。

### R4 · 额度耗尽

知乎搜索 5000 次 / 直答 100 次。开发期反复调试会消耗。

**应对**：开发期用本地缓存 + 请求去重，只在需要新数据时才真调；直答 100 次留给计划书里的「基线对照」，不做高频调用。

### R5 · 时间

13 天，且要跨人协作。

**应对**：P1 契约先冻结，减少并行冲突；P4 的功能按「有它加分、没它不减分」排序，先做勾选重组（PRD 主推的增值项），科普视频分镜可砍。

### R6 · 把 Mock 说成成品

官方检查第 9 条。降级数据可以用于演示，但计划书里不能含糊。

**应对**：双模时界面明确标注当前模式（真实检索 / 演示数据），计划书里也如实写清。

## 五、四维评分策略

评分权重复述（初审）：**AI 场景价值 40% / 创新度 25% / 完成度 25% / 产品体验与设计感 10%**。

### 维度一 · AI 场景价值（40%）

**得分逻辑**：评委在判断「这个 AI 解决的是不是真实、够痛、且非它不可的问题」。

| 高分标准 | 我们的证据 | 实现重点 |
|---|---|---|
| 痛点真实可验证 | 实测：扫地场景 10 条里 4 条是导购；赞 1990 的是最典型的导购文，真正有用的那条只有 1 个赞 | 把证据做进**产品界面**，不只是写进文档 |
| 场景明确（谁/何时/为何用） | 2000 元档家电决策：花错钱会后悔、软文密度最高、交叉比价最费时 | 首屏一句话说清「帮你决定买哪个」 |
| AI 不可替代 | 把「哪个好」翻译成「缺点/耗材/装得下吗」，软文比例从 40% 降到 2.5%；这件事人做要 30 分钟 | 让「改写查询」这个动作在界面上可见 |
| 价值 30 秒内可感 | 26px 结论句 + 三条可执行要点 | 结论必须在第一屏，不能被矩阵视图挡住 |

**验收检查项**

- [ ] 一个不懂技术的人，60 秒内能说出「这产品帮我干什么」
- [ ] 界面上能看到过滤确实发生的证据（被收起内容可展开、可看原因）
- [ ] 计划书里每一条痛点后面都有实测数字，不出现「据调查」「众所周知」
- [ ] 能用一句话说清「为什么知乎自己不做这件事」（利益结构，不是技术）

---

### 维度二 · 创新度（25%）

**得分逻辑**：评委在找「有没有一个别人没想到的点」，而不是「功能多不多」。

| 高分标准 | 我们的证据 | 实现重点 |
|---|---|---|
| 有反直觉但成立的洞察 | ① 高赞 ≠ 可信（赞 1990 是软文）② 改写查询本身是最有效的过滤（40%→2.5%）③ 连「不要买」都可能是广告 | 每个洞察都要在界面上有对应物，不能只活在 PPT |
| 交互上有独特点 | 允许用户推翻系统判断（「我认为这条没问题」） | 让它真的能点、有反馈，不是装饰 |
| 不是功能堆砌 | 主动做减法：矩阵视图不独立成页、trace 收进抽屉 | 界面上不出现机制术语 |

**验收检查项**

- [ ] 能一句话说出「我们和别人不一样的地方」
- [ ] 这个不同点在界面上**看得见**（不是只有文档里有）
- [ ] 至少有一个设计是「评委没见过」的（建议：收起内容可推翻）
- [ ] 没有为了显得厉害而存在的功能

---

### 维度三 · 完成度（25%）

**得分逻辑**：评委在试「点下去会不会坏」。这一项最容易失分，因为没有借口。

| 高分标准 | 说明 | 实现重点 |
|---|---|---|
| 主流程 100% 可跑 | 搜索 → 结论 → 三段 → 收起 → 重组导出，每步都不空 | 消灭所有 alert 占位 |
| 边界状态齐全 | 加载 / 空结果 / 接口失败 / 额度耗尽 / 降级 / 超长文本 | 官方检查第 7 条明文要求 |
| 数据真实 | 不是写死的假数据 | 接真检索，降级才用缓存 |
| 移动端可用 | 评委很可能用手机点 | 375px 宽度实机过一遍 |

**验收检查项**

- [ ] 断网状态下页面仍能打开并给出明确提示（不白屏、不崩）
- [ ] 搜一个搜不到的词，有空结果提示 + 可操作建议，不空白
- [ ] 所有按钮都有真实行为，全站搜不到 `alert(`
- [ ] 连续操作 10 次无 JS 报错（控制台干净）
- [ ] 手机 375px 宽度下，正文不需横向滚动
- [ ] 同一个 query 两次检索结果一致（缓存生效）

---

### 维度四 · 产品体验与设计感（10%）

**得分逻辑**：好不好用、好不好看。权重最低，但最容易做砸。

| 高分标准 | 阈值 | 实现重点 |
|---|---|---|
| 信息层级清楚 | 结论字号 ≥ 24px，正文 ≥ 14px | 结论永远在第一屏 |
| 可读 | 正文最小字号 **≥ 14px**（队友版本 72% 字号 ≤11px，是反面教材） | 全站字号审计 |
| 无术语 | 不出现「可信度 0.62」「四层过滤」「trace」「观点聚类」 | 语言翻译表逐条对照 |
| 手机可读 | 375px 下正常 | 响应式实机验证 |

**验收检查项**

- [ ] 375px 宽度可用，无横向滚动
- [ ] 全站最小正文字号 ≥ 14px
- [ ] 界面文案里搜不到上述 4 个术语
- [ ] 结论在第一屏可见（不用滚动）
- [ ] 配色对比度足够（浅色主题下深色文字）

**排期位置**：最后 2–3 天专门做。因为「产品体验」需在开发时做对，而「设计感」可后期调——只要后端只出 JSON、不出 HTML。

## 六、执行原则

1. **契约先冻结**：P1 不做完，前后端不并行
2. **每步有可验证产出**：每个阶段结束要能点开看，不是「写完了」
3. **先真后美**：功能与真数据优先，视觉留最后
4. **不新增功能**：主路径完成前不加新想法；有想法一律记入 [`备选功能清单.md`](备选功能清单.md)，不删除、只延后决策
5. **可降级是底线**：任何依赖外部服务的环节都要有本地兜底

> 范围管理统一以 [`备选功能清单.md`](备选功能清单.md) 为准：A 类（主路径完成后可做，含 OAuth、LLM 润色、科普分镜等）与 B 类（明确不做，含管理后台、移动 App、爬虫等）均已记录触发条件与原因，避免反复讨论或临时插队。

## 七、需要确认的问题

1. **公网部署怎么走？**（决定 R1 的路线 A/B，也决定 P5 的工作量）
   - 有云服务器/域名吗？
   - 是否接受用内网穿透（本机常开）？
2. **能否去 developer.zhihu.com 再生成一份 Access Secret 给服务器用？**
   （当前凭据在本机 keychain，云端拿不到）
3. **有没有可用的 LLM API Key？**
   - 有 → 「观点提炼」可以真做，创新度更容易拿分
   - 没有 → 只能规则 + 模板模拟，需在计划书里如实说明
4. **团队几个人、怎么分工？** 队友继续负责后端，还是后端也由我这边出？
5. **要不要接知乎 OAuth？** 能增加人气奖机会，但要额外做登录链路与回调。
6. **演示视频做不做？** 做的话建议 90 秒，以实操录屏为主。
