知鉴 Search · 任务清单 A
角色：引擎（后端）
编制：2026-11-23        提交截止：2026-12-07 10:00

【重要前提】
后端从零开始，没有任何可复用的代码。
目前只有一个前端页面里写着 fetch('http://127.0.0.1:8000/api/search')，
那个地址后面是空的，服务不存在。

所以这份清单从「搭第一个能返回数据的接口」开始，
不假设你手上已经有任何后端代码。
============================================================

【你负责什么】
保证这个产品「跑得起来」。

用户输入一个问题 → 后端去知乎拿真实内容 → 判断哪条可信、
哪条是广告、哪条过时 → 把结果按统一结构返回给前端。

【你依赖谁】
· B（界面）：接口契约由 B 主笔（因为后端只出数据，
  字段要按界面需要来定），D1 晚双方冻结
· C（判据）：可信度规则由 C 从标注数据归纳，D3 交付

【谁依赖你】
· B：界面上所有内容都从你的接口来，你不通他就只能一直用假数据
· C：评测报告要跑你的接口
· 全体：部署到公网之后，评委才能打开链接

【一句话】
你在关键路径上，而且是全队唯一的「从零开始」。
A2 晚一天，全线晚一天。


============================================================
技术栈建议（不要在这上面纠结，半天内定死）
============================================================
语言：Python 3.10+
框架：FastAPI + uvicorn
理由：
  · 起一个接口只要十几行
  · 自带 /docs 调试页面，联调很方便
  · 部署便宜，1 核 2G 云服务器够用

起步命令（照抄即可）：
  pip install fastapi uvicorn
  uvicorn main:app --reload --port 8000

最小骨架（先让它跑起来，再往里填逻辑）：

  from fastapi import FastAPI
  from fastapi.middleware.cors import CORSMiddleware

  app = FastAPI()
  app.add_middleware(
      CORSMiddleware,
      allow_origins=["*"],      # 本地开发先放开，上线再收紧
      allow_methods=["*"],
      allow_headers=["*"],
  )

  @app.get("/")
  def health():
      return {"ok": True, "mode": "real"}

  @app.post("/api/search")
  def search(body: dict):
      return {"query": body.get("query"), "answers": [], "mode": "real"}

【最容易卡住的三处，先看这里】
  1. CORS —— 前端从 file:// 或别的端口访问时会被浏览器拦掉，
     报错长得跟「后端没启动」几乎一样。先把 allow_origins 放开。
  2. 中文编码 —— 知乎 CLI 输出是 UTF-8，Python 里用 subprocess
     取 stdout 后要 .decode("utf-8")，不要用系统默认编码，
     否则全是乱码。
  3. 请求超时 —— 一次检索 1-3 秒，前端等不及会以为挂了。
     前端设 8 秒超时，后端不要在这上面加长逻辑。

A0 · 搭骨架，返回假数据（D1 上午）
------------------------------------------------------------
做什么：
  用上面的骨架起一个能跑的服务，/api/search 先返回
  2 条硬编码的假数据。

产出：
  浏览器打开 http://127.0.0.1:8000/docs 能看到接口文档，
  用 Try it out 能拿到那 2 条假数据

算完成：
  B 能用你的地址渲染出东西（哪怕是假的）

注意：
  这一步的目的是让两条线当天就能接上，不是把功能做完。
  宁可接口很丑，也要今天就通。


------------------------------------------------------------
A1 · 冻结接口契约（D1 晚）★ 必须按时
------------------------------------------------------------
做什么：
  B 主笔写 docs/api-contract.md，你确认技术上能做到，
  双方确认，之后不再改。

  需要确认的字段（B 会按界面需要细化）：
    query       用户原话
    intent      查询类型：compare / experience / controversy
    mode        real / degraded（前端据此显示模式标记）
    answers[]   每条含：url, title, content_text, author_signature,
                vote_up_count, age_days, content_type,
                is_ad_suspect, reasons[], group
    cards[]     一句话结论与四类要点
    trace[]     各阶段处理量与剔除原因

产出：
  docs/api-contract.md

算完成：
  B 能照着写完全部渲染逻辑，不需要再问你

注意：
  · 后端只出 JSON，绝不出 HTML 片段
    （否则以后改任何视觉都要动后端）
  · 不要把可信度分数给前端，只给 is_ad_suspect + reasons[]
    用户看到 0.62 只会困惑
  · 契约能改的唯一理由是「技术上做不到」，不能因为「想改」就改


------------------------------------------------------------
A2 · 接入知乎，返回真实数据（D2）★ 关键路径，最高优先级
------------------------------------------------------------
做什么：
  把硬编码的假数据，换成真实调用知乎开放平台。

  调用方式（已验证可用）：
    zhihu-cli search zhihu --query "<查询>" --count 10

  Python 里这样取（注意 encoding）：
    import subprocess, json
    r = subprocess.run(
        [cli_path, "search", "zhihu", "--query", q, "--count", "10"],
        capture_output=True,
    )
    data = json.loads(r.stdout.decode("utf-8"))

  字段映射：
    Title        -> title
    ContentText  -> content_text
    Url          -> url
    AuthorName   -> author_signature
    VoteUpCount  -> vote_up_count
    CommentCount -> comment_count
    CreateTime   -> 换算成 age_days（距今天数）
    ContentType  -> content_type（Article / Answer）

产出：
  /api/search 返回真实知乎内容

算完成：
  搜「两千价位扫地机器人 石头 追觅 怎么选」，
  返回 10 条真实标题和正文

注意：
  · CLI 已经装好，凭据也在本机，直接能用，不要重复安装
  · 单次检索最多 10 条，HasMore 恒为 false，翻不了页
  · 一次检索 1-3 秒，要考虑并发时会不会堵
  · 这一项如果 D3 结束还没通，立刻群里说，不要自己扛


------------------------------------------------------------
A3 · 查询改写：拆子查询（D3）
------------------------------------------------------------
做什么：
  把用户一句话拆成 3-4 个子查询，分别召回后合并去重。

  例：「两千价位扫地机器人 石头 追觅 怎么选」拆成
    1. 石头扫地机器人 用了半年 真实感受
    2. 追觅扫地机器人 缺点 问题 后悔
    3. 扫地机器人 耗材 一年 花多少钱
    4. 扫地机器人 基站 尺寸 上下水 预留

产出：
  合并去重后 30-40 条内容

算完成：
  同一个 query，返回条目从 10 增加到 25 以上，
  且内容角度明显不同（不全是导购文）

注意：
  · 这是本项目最关键的机制。实测：原始 query 软文比例 40%，
    拆成子查询后只有 2.5%——改写本身就是最有效的过滤
  · 拆解规则不要写死在代码里，做成可配置的模板
  · 4 次调用消耗 4 次额度（共 5000 次，够用）
  · 开发期一定要加缓存，否则调试时反复调用很快见底


------------------------------------------------------------
A4 · 时效过滤（D3）
------------------------------------------------------------
做什么：
  剔除内容过时的条目。
  判据不能只看发布时间，要看内容里提到的机型年份
  （实测有 2016 年的文章还在推荐早已停产的型号）

产出：
  每条被剔除的内容附带原因，写进 trace

算完成：
  trace 里能看到「剔除 N 条，因为机型已停产 / 内容超过 X 年」

注意：
  不要为了凑数量把老内容留下，宁可结果少几条


------------------------------------------------------------
A5 · 可信度质检（D4）
------------------------------------------------------------
做什么：
  按 C 给出的判据清单（D3 交付）逐条判定，输出：
    is_ad_suspect: true / false
    reasons: ["文末有购买链接", "全文没有一处提到缺点", ...]

  参考判据（以 C 的清单为准）：
    · 账号昵称含「定制/工厂/家居/装饰/优选/甄选」
    · 正文出现「双十一/京享红包/优惠券/到手价」两个以上
    · 标题含「推荐/选购指南/最值得买/清单/横评」
    · 全文无缺点、无实拍、无具体使用场景
    · 以参数罗列为主，缺第一人称经历

产出：
  每条 answer 带 is_ad_suspect 和 1-3 条人能看懂的理由

算完成：
  在 C 的 50 条标注集上，识别召回 ≥80%，误杀 ≤10%

注意：
  · 理由必须是人话，不能出现 score=0.31
  · 判为软文的不要删除，标记后照样返回，前端会折叠展示
  · 小心伪装型：标题写「这些型号不要买」，正文全是推荐
  · 误杀比漏杀更伤体验，宁可放过几条


------------------------------------------------------------
A6 · 归并成三段结构（D5）
------------------------------------------------------------
做什么：
  把 30-40 条内容归并成三个桶，供前端直接渲染：
    1. 大家都这么说（多篇独立来源一致）
    2. 说法不一的地方（同一问题结论相反）
    3. 有人具体踩过的坑（带场景的具体问题）

产出：
  answers[].group 标记 + cards[] 里的归纳

算完成：
  前端拿到后直接渲染，不用自己算分组

注意：
  · 先提炼「一句话结论」，它决定结果页的第一眼
  · 同一问题下多条回答（考研场景实测有 3 条同题）要归并成分歧
  · 分不出三段就只给两段，不要硬凑


------------------------------------------------------------
A7 · 缓存层（D6）
------------------------------------------------------------
做什么：
  同一个 query，24 小时内返回同一份结果

算完成：
  同一个 query 连搜两次，返回内容完全一致

注意：
  这是为了现场演示可复现，不是为了性能。
  演示前要提前跑一遍预热。


------------------------------------------------------------
A8 · 降级（D6）
------------------------------------------------------------
做什么：
  知乎调用失败 / 额度耗尽 / 超时，三种情况都不返回 500，
  改为返回上一次缓存，并把 mode 设为 "degraded"

算完成：
  断网搜一个词，接口仍返回 200，但 mode 是 degraded

注意：
  官方提交检查第 7 条明文要求：接口失败、额度耗尽、空数据，
  都必须有真实的错误或降级提示。这是必查项。


------------------------------------------------------------
A9 · 部署公网（D8）★ 风险最高
------------------------------------------------------------
做什么：
  把后端部署到公网，让评委能直接访问。
  凭据用环境变量 ZHIHU_ACCESS_SECRET 传入。

算完成：
  手机流量（关掉 wifi）打开前端，能搜出真实结果

注意：
  · Secret 不能写在代码里、日志里，也不能出现在前端返回里
  · 部署前要验证：CLI 能否在服务器（无图形界面）上工作。
    若不行，改成直接调知乎开放平台 HTTP 接口
    （参考 skill 目录下的 references/http-api.md）
  · 这一项务必 D8 前完成，不要拖到最后
  · 若只能用内网穿透，必须写清「依赖某台电脑常开」并告知全队

  官方提交前检查清单第 6、7 条能打勾
